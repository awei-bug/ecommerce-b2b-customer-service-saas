# 商用路径：私有化 1 家 · 线上带货 · 6 个月内无支付主体

> 日期：2026-07-18  
> 决策（用户确认）：  
> 1. **交付形态**：私有化先做 **1 家** 真实店铺（不是一上来公开 SaaS 招商）  
> 2. **主体/支付**：约 **6 个月内没有** 公司/个体户与微信支付商户号  
> 3. **业务**：线上电商 **带货**（标品上架、接单、发货履约）  
>  
> 本文是 **当前唯一商用执行约束**；与《完整电商标准产品架构》冲突时，以本文为准。

---

## 1. 这意味着什么

| 维度 | 结论 |
|------|------|
| 不做什么 | 不对外宣称「已支持微信官方支付收款」；不接假商户号；不铺五域全功能 |
| 支付怎么处理 | **生产强制 mock 关闭对外假成功**；业务上用 **人工确认收款**（客户转账/微信个人收款后，店长在后台点「标记已付」） |
| 多租户代码 | **保留**（便于以后扩展），但商用验收只保证 **1 个生产租户** 稳定可用 |
| 成功标准 | **1 家真实带货店连续用 ≥14 天**：能上架、能记订单、能标已付、能发货、库存不乱 |

**合规说明（必读）：**  
个人微信收款 / 私下转账 **不是** 正规电商支付方案，存在限额、纠纷与合规风险。6 个月内可作为 **熟人/内测带货的运营权宜**；公开规模化收款必须等主体 + 商户号。产品文案中应写清「订单支付状态由商家人工确认，非第三方支付」。

## 2. 带货场景：店长每天要干什么

```text
备货上架 → 顾客下单（或店长代录）→ 确认收到钱 → 标已付 → 打包发货 → 售后/退款登记
```

| 角色 | 系统里做什么 |
|------|----------------|
| 店长 | 上架/改价/库存、看待付款/待发货、标记已付、发货填单号、导出对账 |
| 顾客 | H5/电脑商城浏览、登录、下单、查订单（付款走店主约定的线下方式） |
| 你（实施方） | 部署、开通租户、培训、修阻断 Bug |

## 3. 6 个月功能边界

### 3.1 必须做（商用最小集）

| 模块 | 要求 |
|------|------|
| 部署 | 云主机 + Nginx + HTTPS + Gunicorn + MySQL + 每日备份 |
| 配置 | 生产 `DEBUG=0`、`ALLOW_MOCK_PAY=0`、固定 `SECRET_KEY`、`.env` 不入库 |
| 商品 | 上架/下架、价格、库存、主图、简介 |
| 订单 | 状态机；**人工标记已付款**；发货；取消；仅退款登记 |
| 库存 | 下单扣减 + 取消/退款回滚（CAS 已有） |
| 运费 | 模板计价（已有） |
| 权限 | 店长全权；店员仅看单发货（RBAC 已有，按需裁剪） |
| C 端 | 列表/详情/登录/下单/订单查询；支付按钮改为「提交订单，请按商家指引付款」 |
| 审计 | 标已付、发货、退款必记日志 |
| 导出 | 订单 CSV（已有） |
| 文档 | 《店长操作手册》1 页 + 《部署清单》 |

### 3.2 明确不做（6 个月内）

- 真微信/支付宝官方支付  
- 平台运营中台、套餐计费、公开招商  
- 分销、拼团、短视频、图搜、AI 文案  
- 微服务拆分、换技术栈  
- 复杂会员积分商城  

### 3.3 可选增强（有余力再做）

- 店长 **代客下单**（电话/微信群成交后录入）  
- 订单备注、快递单号批量粘贴  
- 简单「今日待发货」大屏数字（已有 summary 可打磨）  
- 商品封面图 OSS（可先本地上传，上线再迁）

## 4. 「无商户号」下的交易设计（关键产品决策）

### 4.1 推荐流程

```text
顾客下单 → status=pending_pay
  → 页面提示：请按商家说明完成付款（微信/支付宝转账等）
  → 店长核对到账后：后台「标记已付款」→ status=paid
  → 店长发货 → shipped → 完成
```

### 4.2 系统能力要求

| 能力 | 说明 |
|------|------|
| `POST /order/<id>/mark-paid/` | 仅 `pending_pay` → `paid`；写审计；需 `order:ship` 或新权限 `order:mark_paid` |
| C 端文案 | 不出现「模拟支付成功」给真实顾客；开发环境才显示 mock |
| 生产开关 | `ALLOW_MOCK_PAY=0` 时，mock 接口全部 403 |

### 4.3 不推荐

- 生产环境开着 mock 让顾客「点一下就当付了」  
- 对外宣传支持微信支付

## 5. 与现有代码的关系

| 已有资产 | 商用用法 |
|----------|----------|
| 多租户 | 生产只开 1 个租户；代码保留隔离 |
| 订单状态机 / 支付单 | 保留；真支付 6 个月后再接 |
| mock 支付 | **仅开发** |
| RBAC / 运费 / 上下架 / 导出 / 审计 | 直接纳入店长日常 |
| 平台开通 API | 你自己开通这一家用 |

**优先补代码（下一迭代）：**

1. 人工「标记已付款」接口 + 后台按钮  
2. 生产配置模板（`ALLOW_MOCK_PAY=0`、mock 禁用）  
3. C 端下单成功页：付款指引文案（可配置店铺说明）  
4. 部署文档（Docker 或一键脚本二选一）  
5. 店长手册

## 6. 12 周商用节奏（私有化 1 家）

| 周次 | 目标 |
|------|------|
| 1–2 | 生产部署草案 + 标记已付 + 生产关 mock + 双租户回归脚本固化 |
| 3–4 | 店长履约体验（待发货台、备注、发货必填单号）+ C 端付款指引 |
| 5–6 | 找 1 家真实带货对象试用；修阻断问题 |
| 7–8 | 备份演练、操作手册、基础监控 |
| 9–12 | 稳定运行；收集需求；**不**开真支付除非主体提前到位 |

**出口（可称为「可商用内测」）：**  
真实店连续 14 天：日均有订单录入或线上单，发货不靠表格。

## 7. 风险与话说清楚

| 风险 | 应对 |
|------|------|
| 个人收款纠纷 | 协议与备注写清；大额谨慎；尽快办主体 |
| 被当成「能正收款的电商」 | 产品与销售话术统一 |
| 功能膨胀 | 只服务带货履约，拒绝架构图诱惑 |
| 单点故障 | 备份 + 简单监控，避免只跑在个人电脑 |

### 8.1 已落地接口（2026-07-18）

| 能力 | 路径 |
|------|------|
| 标记已付款 | `POST /order/<id>/mark-paid/` 权限 `order:mark_paid` |

| C 端店铺信息 | `GET /api/c/shop/` 返回 `pay_guide`、`payment_mode=manual` |

**迁移：** `python scripts/migrate_commercial_manual_pay.py`  
**刷新店员权限：** `python scripts/seed_rbac_roles.py --with-users`
