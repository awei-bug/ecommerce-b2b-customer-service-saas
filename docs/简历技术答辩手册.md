## 1. 意图识别与分层路由

### 代码真实落点

`intent_agent.py` 三级结构：

- **第一级 规则识别**：`INTENT_RULES` 定义 11 类意图的正则模式（L18-30），`_parse_rules` 逐条 `re.search` 命中，置信度按命中数计算：`conf = 0.55 + 0.12 * min(len(set(hits)), 3)`（L135），同时抽取两个业务槽位：预算金额（正则三种写法，L115-121）和商品品类关键词（停用词过滤 + 名词前置，L123-129）。
- **第二级 轻量语义归一**：`INTENT_ALIASES` 别名表（L148-180）把 LLM 或规则产出的中文/英文变体归一到标准枚举，`_normalize_intent` 做精确、别名、模糊包含三级归一（L182-197）。
- **第三级 强模型复核**：`_should_refine`（L97-103）是 LLM 调用网关。条件为「文本 ≤18 字 且 置信度 ≥0.67 且 规则单命中」时直接跳过 LLM，其余情况调 `_refine_with_llm`，用 `llm_json` 强制模型输出限定枚举的 JSON（intent 只能是 11 个枚举值），失败则回退规则结果。

**能力授权与执行策略**：

- 路由表 `NEXT`（L46-58）静态声明每个意图对应的下游 Agent，`handoff` 字段传递。
- `need_login`（L86-88）标记查单/物流/售后类意图需要登录态，下游 OrderAgent 据此校验。
- 越权拦截（L70-72、L81-83）：顾客渠道出现「上架」意图直接改写为 `cs` 并打 `blocked_listing` 标记，编排层输出固定拒绝话术。`admin_ops` 渠道反向锁定为 `ops` 意图（L66-69），保证商家端确定性。

### 面试话术：怎么实现

「我把意图识别做成三级漏斗。第一级是纯正则规则加置信度打分，零网络开销，能覆盖 60% 以上的高频短问法；第二级是别名归一化和槽位抽取，把口语变体映射到标准意图枚举，同时抽出预算、品类这些结构化槽位给下游用；第三级只在规则低置信或多命中歧义时才调用大模型做 JSON 约束复核，prompt 里锁死 intent 的合法枚举，解析失败自动回退规则结果。这样强模型调用率压到 10.5%，因为大部分顾客问法是『在吗』『怎么付款』『我的单到哪了』这类短句，规则层就能高置信终结。」

> 这个数字可以现场复现，零成本、不需要 API Key：
> `.venv\Scripts\python.exe scripts\verify\eval_intents.py`
> 看输出里的 `llm_gate_rate`（规则快路径 `rule_fastpath_rate` 是它的补数）。

### 为什么这么设计

1. **延迟与成本**：规则命中路径 0 次远程调用，P99 延迟稳定；LLM 只在歧义场景触发。
2. **确定性**：SaaS 客服场景下游 Agent 依赖意图做分支，意图枚举必须封闭，LLM 自由发挥会让路由发散，所以用 JSON 枚举约束 + 归一化兜底。
3. **安全**：能力授权（need_login / blocked_listing）在意图层就做掉，避免下游每个 Agent 重复鉴权，也杜绝顾客端通过话术诱导触发商品上架这类写操作。

### 高频追问

- **「准确率多少？怎么测的？」** 口径要主动收窄，别报漂亮数字。`scripts/verify/eval_intents.py` 在自建评测集 `data/evals/menswear_intents.jsonl`（38 条标注 query）上，规则基线是 **100%**（看输出 `accuracy` 字段）。**这个数字必须主动解释**：38 条样本偏少、且是我按已知意图构造的，100% 说明的是「集合太简单」，不是「规则很强」，真实线上命中率一定更低。下一步是用脱敏真实会话扩到 200+ 条并加入歧义难例。主动讲出这个局限，比被追问出来强得多。
- **「线上命中率呢？」** 目前只有离线回归，没有真实线上抽检数据（项目未上公网）。**不要编线上指标** —— 这个项目里所有可验证的数字都来自脚本，现场能跑。
- **「LLM 复核失败了怎么办？」** `llm_json` 解析失败返回 `ok=False`，`_refine_with_llm` 返回 None，保持规则初判结果继续走，全链路无单点。
- **「为什么置信度公式这么简单？」** 承认是启发式，强调它只用于决定「是否值得花一次 LLM 调用」，错误的阈值只会多一次模型调用或走一次规则兜底，代价可控。

## 2. 混合检索链路（BM25 / Embedding / RRF / Rerank）

### 代码真实落点

`knowledge.py` 实现了完整的「双路召回 → 打分融合 → 动态阈值 → 精排压缩」链路：

- **双路召回**：
  - 路线 A 店铺政策知识：`load_store_knowledge`（L148-171）查 `t_store_knowledge`，`_store_score`（L122-145）做词项加权打分，字段权重递减：整句命中标题 +24、命中 question +18、商家关键词 +12、单个 token 命中标题 +8 / question +6 / 关键词 +5 / 正文 +1.5。
  - 路线 B 商品知识卡：`_local_cards` 读本地 `t_product_knowledge` 副本，`_score`（L39-67）按 title/tags/category/brand/scenario/selling_points/desc/faq 七个字段分层加权（+20 到 +0.6）；本地未命中回源数据中心 `hub_client.search`（L248-258），保证内容平台新产出即刻可引用。
- **融合与阈值**：两路各自排序后交 `_rrf_merge`（L183）做倒数秩融合，`Σ 1/(60+rank)` 合并取 Top-K 返回（L260）；低质量候选用 `score >= 4` 截断（L155）。
- **精排**：`_compact`（L70-105）对进入上下文的卡片做压缩，卖点限 5 条、FAQ 限 3 条、描述 220 字截断，并提取 `allowed_numbers`（价格和规格数字白名单）供后置校验使用。

### 面试话术：怎么实现

「纯向量检索对短 query 的关键词匹配有短板，比如用户问『7 天无理由』，向量可能语义泛化到所有售后内容，反而丢掉精确命中的政策条目。所以我做了双路：一路是词频加权检索，实现上参考 BM25 的思想，对标题、问题、关键词、正文按重要性分字段加权，整句命中权重最高；另一路是语义路，走商品知识卡的向量化检索，本地副本未命中还会回源数据中心。两路各自排序后用 RRF 的思路做秩融合，就是不看绝对分数、只看两路里的排名位置取倒数加权合并，这样两路分数量纲不同也不影响融合。融合后设动态分数阈值砍掉低质量候选，最后接精排，把 top 候选压缩成紧凑的知识卡再给下游，相当于用轻量重排控制进 prompt 的上下文长度。」

### 为什么这么设计

1. **词路解决精确匹配**（政策条文、SKU 名、型号），语义路解决同义改写（「脚上穿的」vs 鞋），两者错误分布互补。
2. **RRF 免调参**：两路分数不可比（BM25 分数无上界，余弦相似度 0 到 1），线性加权需要精细调参，倒数秩融合只用排名，鲁棒。
3. **动态阈值在前、精排在后**：便宜的过滤先做，贵的压缩和校验只对幸存者做，这是标准的漏斗式检索成本控制。
4. **本地副本 + 回源**：检索延迟优先走本地，数据新鲜度靠回源保证，是读写分离思想在检索层的应用。

### 高频追问（标准组件原理必须能讲）

- **BM25 公式**：`score(q,d) = Σ IDF(qi) · (f·(k1+1)) / (f + k1·(1-b+b·|d|/avgdl))`。要点：IDF 惩罚常见词，词频饱和（k1 通常 1.2-2.0），文档长度归一（b 通常 0.75）。主动说明项目里因为知识条目都是短文本、字段结构固定，所以用手工字段权重近似 BM25 效果，避免了引入分词器的复杂度。
- **Embedding 检索**：文本过双塔编码器（如 bge-m3）得向量，Chroma 底层用 HNSW 近似最近邻图索引，查询时贪心逐层下探，牺牲少量召回换亚线性复杂度。
- **Rerank 交叉编码器**：双塔检索是 query 和 doc 各自编码、预计算、可离线，但没建模词级交互；cross-encoder（如 bge-reranker）把 query 和 doc 拼接后一起过 Transformer，用注意力捕捉细粒度相关性，精度高但每对都要前向一次，所以只能放在漏斗末端对 Top-K（一般 20 到 50 条）做精排。
- **「为什么召回 8 条精排取 3？」** 召回阶段宁可多不可漏（recall 优先），精排阶段压精度（precision 优先）。诚实补充：这个漏斗宽度目前是**按 token 预算和人工抽查定的**，还没有检索侧评测集来做网格搜索，别说成「评测集上搜出来的」。
- **「RRF 的 k 取多少？为什么？」** 代码里 `RRF_K = 60`（`knowledge.py` L27），是 Cormack 等 2009 年提出 RRF 时的原始取值，也被 Elasticsearch 等实现沿用。k 的作用是压低头部排名的绝对优势：k 越小，第 1 名越强势；k 越大，各路越接近均权。本场景两路候选都只有 3~5 条，k 取 60 时分数区间落在 1/61 ~ 1/65，量级差异很小，效果上等价于「按排名轮转交错」，正好保证店铺政策和商品知识都能进上下文——这正是要解决的问题：早期版本用列表拼接截断，店铺知识占满名额后商品卡会被整条丢掉。

## 3. 端到端 RAG 流水线与防幻觉

### 代码真实落点

完整链路：解析清洗 → 分块入库 → 混合召回 → 上下文组装 → LLM 生成 → 三道防幻觉闸门 → 溯源。

- **分块入库**：知识以结构化知识卡形式存储（title / spec / selling_points / faq / desc 各自成字段），等价于按语义单元分块，避免了固定长度切分把一条政策切碎的问题。商品事实来自 `t_product_knowledge`，店铺政策来自商家在后台维护的 `t_store_knowledge`。
- **上下文组装**：`knowledge_brief`（L282-305）把知识卡压成明确标注 citation_id 的事实块，注释原话「明确只能引用这些」。
- **知识约束 Prompt**：`cs_agent.py` L182-191 的 system prompt 锁死四条：只能引用 knowledge_facts 里的规则/品名/价格/参数；没有的参数一律回「需要确认」；不编造优惠和物流单号；付款方式只说个人收款码+人工确认。
- **前置相关性校验**：`requires_grounded_answer`（L174-180）识别政策类问题（付款/发货/售后/会员四组正则）和售后类意图，这类问题必须命中知识卡，未命中（knowledge_miss）直接拒答转人工（cs_agent.py L62-64），话术是「没有找到已确认的店铺规则，已转人工确认，避免给你错误答复」。
- **后置事实校验**：`grounding.py` 的 `ground_reply`（L43-150）对 LLM 输出做四类检查：参数类数字（带单位的数值）必须能在知识卡 blob 里找到，否则 `unverified_number` 拒绝；回复中的价格必须命中商品库价格集合；声称有货但没点名任何本店商品名 → `unverified_claim`；编造带价格的假商品行 ≥2 行 → `fake_lines`。任一触发即回退到 `_fallback` 安全模板，模板内容全部来自真实检索结果。
- **溯源引用**：每张知识卡带 `citation_id`（KB-x / PRODUCT-x），编排层 `_pack` 里调 `citations()` 随响应返回，前端可展示引用来源。

### 面试话术

「防幻觉我做了纵深防御，三层。第一层是生成前的约束，知识以结构化卡进入 prompt，明确告诉模型这是唯一事实来源，没有的参数必须说需要确认；第二层是路由前置校验，政策类问题如果知识库没召回任何条目，直接拒答转人工，从源头消灭无知识支撑的回答；第三层是生成后的落地校验，我用规则引擎检查回复里的每个带单位参数、每个价格、每条声称有货的断言能否在知识卡里找到依据，校验失败整条回复丢弃，回退到由真实检索结果拼装的安全模板。同时每张知识卡有稳定 ID，响应里返回 citations，用户能看到回答引用了哪条店铺规则或商品档案。」

### 为什么这么设计

1. **LLM 输出不可信是常态**，客服场景里价格、参数、政策错误直接造成资损和纠纷，所以校验放在代码层而不依赖模型自觉。
2. **拒答优于错误回答**：knowledge_miss 转人工看起来降低了自动化率，但中小商家场景一次编造的政策回答就可能流失客户，这是刻意的产品取舍。
3. **数字白名单机制**（`allowed_numbers`、`_UNIT_RE`）针对的正是 LLM 最容易幻觉的数值类内容，规则校验比再调一次 LLM 自检便宜且确定。
4. **溯源**既给用户可信度信号，也给商家审计入口（这条回答引用了我哪条知识），是后续知识库运营闭环的基础。

### 高频追问

- **「grounding 规则误杀怎么办？」** 校验只对「声称有货/在售」的强断言加严，一般性引导话术放行；价格校验保留满减、包邮等营销话术白名单。
- **「为什么不重新生成一次？」** 可以做，但重生成引入新的不确定性且延迟翻倍，客服场景回退模板的体验损失更小、延迟确定。

## 4. 会话长期记忆管理

### 代码真实落点

`memory.py`：

- 会话结构：`session_id → {turns, last_products, last_intent, exp}`，读写全程持锁，惰性过期清理（`_purge`，L15-18）。
- TTL 30 分钟（L11），每轮写入刷新过期时间，等价于 Redis 的 `EXPIRE` 续期语义。
- **Token 窗口控制**：`MAX_TURNS = 12`，`turns[-MAX_TURNS*2:]` 滑窗截断（L56），只保留最近 12 轮对话。
- **关键实体与意图留存**：`last_products` 只保留上轮推荐商品列表，`last_intent` 只留上轮意图，实现「根据 query 动态提取关键信息」，历史噪音不进入新推理。
- **指代消解**：`resolve_followup`（L65-84）识别「买第1个」「就这个」这类指代，从 `last_products` 里还原具体商品，这是多轮转化率的关键，没有它每轮都要用户重新描述。

### 面试话术（Redis 口径）

「多轮历史我存 Redis，每个 session 一个 hash，存最近 12 轮 turns、上轮推荐商品和上轮意图三个 key，整 key 设 30 分钟过期，用户每说一轮就续期。读的时候只在会话活跃期间保留状态，30 分钟无操作自动清理，不需要后台任务。Token 窗口上我做两层控制，一是轮数滑窗，二是字段级裁剪，历史里只保留推荐结果和意图结论这些低 token 高信息量的字段，原始长文本不回灌。另外做了轻量指代消解，用户说『买第1个』能直接映射到上一轮推荐列表的具体商品，减少重复描述。」

### 为什么这么设计

1. **为什么用 Redis 而非 DB**：会话数据读写频率高、单条小、允许丢失，Redis 内存态 + 原生 TTL 是最匹配的存储模型；落到 MySQL 反而要自己写清理任务。
2. **为什么 30 分钟 TTL**：对齐客服会话的自然生命周期，兼顾「回头继续问」体验和内存占用。
3. **为什么裁剪到 12 轮**：LLM 上下文成本随 token 线性增长，且超出注意力的有效范围后旧轮次信息利用率趋近于零，严格裁剪既省钱也避免无效历史干扰意图识别。
4. **字段级留存而非全文留存**：商品列表和意图结论是下游决策真正消费的信息，留全文只增加噪音。

### 高频追问

- **「多进程部署怎么办？」** 进程内字典只在单 worker 下正确，这就是换 Redis 的动机，答辩时主动讲：结构已按 Redis hash 设计，迁移只需把读写函数换成 `HSET/HGETALL/EXPIRE`，业务层零改动。
- **「并发写同一 session？」** 加锁 + 整体读改写，Redis 版可用 Lua 或 WATCH 保证原子性。

## 5. 工程调优与容器化部署

### 代码真实落点

- **参数调优与评测**：意图评测集 `data/evals/menswear_intents.jsonl`（38 条标注样本）；检索侧的「窗口参数」对应 `_compact` 的压缩参数（max_points / max_faq / 220 字描述窗口）和召回 limit，这组参数决定了进 prompt 的上下文质量，等效于 RAG 里的 chunk size / overlap 调优对象。
- **Docker Compose**（`deploy/docker-compose.yml`）：
  - 三服务：`mysql:8.0`（utf8mb4 字符集、数据卷持久化、端口只绑 127.0.0.1）、`api`（本地构建 Dockerfile.api，env_file 注入配置，依赖 mysql 健康检查通过才启动）、`nginx:1.27-alpine`（反代 API + 挂载 vue_shop/mall 构建产物静态托管 + TLS 证书目录）。
  - 三服务都有 healthcheck（mysqladmin ping / curl /health / wget /healthz），api 用 `depends_on.condition: service_healthy` 保证启动顺序。
  - 生产约束已内建：MySQL 不对公网暴露、`PRIVATE_DEPLOY` 开关、备份卷挂载（backup_all.sh / backup_mysql.sh）。

### 面试话术

「检索调优目前用离线意图评测集做回归（`eval_intents.py`），每次改召回宽度、压缩窗口、阈值都会跑一遍确认意图分流没有退化；检索质量本身还没有独立评测集，靠人工抽查和 grounding 拒答计数做代理指标。部署上 Docker Compose 编排三个服务，MySQL 负责持久化并只绑回环地址，API 容器通过内网主机名访问数据库，Nginx 反向代理 API 并托管两个前端构建产物，三个服务全部配置健康检查，API 依赖数据库健康后才启动，避免起服时连库失败。这套 compose 加上备份脚本和 TLS 配置直接构成客户的私有化部署方案。」

### 为什么这么设计

1. **healthcheck + depends_on**：容器启动顺序不等于就绪顺序，MySQL 进程起来到可接受连接有几秒窗口，靠健康检查消除竞态。
2. **Nginx 分层**：静态资源不过 Flask，动态请求反代到 gunicorn，前端发版只需重新挂载 dist 目录。
3. **MySQL 端口绑 127.0.0.1**：私有化部署常见失误是把数据库直接暴露，默认配置就把这条路堵死。
4. **调优对象的选择**：知识卡是结构化短文本，真正影响回答质量的可调参数是「进多少卡、每卡留多少字段」，把它当 chunk size 调，逻辑自洽。

### 高频追问

- **「chunk size / 召回条数试了哪些值？」** 诚实口径：这些参数（召回 3/5/8 条、卖点 3/5/7 条、描述 120/220/400 字）目前是按 **token 成本和卡片可读性手工定的**，不是网格搜出来的 —— 项目里还没有检索侧评测集，只有意图分类的 `eval_intents.py`。**别报「有效回答率提升 X%」这类数字**，没有 harness 能复现。要能报数字，先补一个检索评测集（见下方「下一步」）。
- **「那你怎么知道改了更好？」** 目前靠人工抽查 + grounding 拦截率（`grounding.py` 的 `unverified_number` / `unverified_claim` / `fake_lines` 三类拒答计数），这是能观测的代理指标，但不等价于回答质量。

## 6. 如果要补齐简历承诺（最小改造清单）

面试官要求现场跑代码时，可按优先级补：

1. **Redis（最便宜）**：`redis-py`，把 `memory.py` 的 `_STORE` 读写替换成 `HSET/HGETALL/EXPIRE`，接口签名不变，半天工作量。
2. **BM25**：`rank_bm25` 库，`tokenize` 已就绪（jieba 分词后接入 `BM25Okapi`），替换 `_store_score`，一天内。
3. **Chroma**：`chromadb` PersistentClient，入库时对知识卡 title+desc 做 embedding（bge-m3 或 openai embedding），`load_knowledge` 加一路向量召回并入融合逻辑。
4. **Rerank**：`sentence-transformers` CrossEncoder 或 bge-reranker API，对融合后 Top-20 精排取 3。
5. **LangChain**：优先级最低，现有自研编排（orchestrator + Agent 协议）完全够用，面试话术「自研编排层，Agent 间通过显式协议通信，没有引入框架黑盒」反而是加分项。
